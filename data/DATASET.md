## Summary

The project uses **three synthetic datasets**, committed to the repository at
[`data/synthetic/`](.) and regenerated by one command. They are **generated, not
collected** — a deliberate choice explained in *Provenance* below, and the single
most important thing to be clear about when presenting them.

| File | Rows | Cols | Size | Feeds |
|---|---|---|---|---|
| [`synthetic/commands.csv`](synthetic/commands.csv) | 9,996 | 2 | 564 KB | **2.1** Intent Classifier (CLO04) |
| [`synthetic/action_tasks.csv`](synthetic/action_tasks.csv) | 7,655 | 10 | 544 KB | **2.2** ETA Regression (CLO03), **2.5** RL Router (CLO05) |
| [`synthetic/action_sessions.csv`](synthetic/action_sessions.csv) | 3,000 | 2 | 108 KB | **2.4** Association Rule Mining (CLO05) |

All three are tracked in git — a fresh clone has them without running anything.

## Regenerating

```bash
py -3.12 -m datagen.generate
```

Deterministic: `seed=42`. Re-running reproduces the files byte-for-byte, so a
reported metric can be traced back to the exact data that produced it. Sizes are
adjustable — `--commands 4000 --sessions 1500`.

The generators live in [`datagen/`](../datagen/):

| File | Role |
|---|---|
| `datagen/config.py` | Shared vocabulary — intents, agent mapping, task timing profiles. Single source of truth |
| `datagen/commands.py` | Builds `commands.csv` from templates + fillers + noise |
| `datagen/action_logs.py` | Builds `action_tasks.csv` and `action_sessions.csv` |
| `datagen/generate.py` | Entry point that writes all three |

## 1. `commands.csv` — labelled natural-language commands

**Task**: multi-class text classification. **Used by**: component 2.1.

| Column | Type | Description |
|---|---|---|
| `text` | string | A user command as typed, e.g. `tl;dr the PDF asap` |
| `intent` | categorical | One of 7 labels |

**Class balance** — near-uniform by construction:

| Intent | Rows |
|---|---|
| document_intel | 1,447 |
| chitchat | 1,447 |
| browser | 1,442 |
| memory_query | 1,429 |
| desktop_automation | 1,428 |
| communication | 1,402 |
| llm_fallback | 1,401 |

**Deliberate difficulty.** 6% of rows have their label flipped at random
(`label_noise=0.06`), and classes share vocabulary on purpose. This matters for
the write-up: an earlier version of the generator produced trivially separable
data and the classifier scored a meaningless **1.000**. With shared vocabulary
and label noise it scores **0.929 macro-F1** (LR/SVM), with a real spread down
to 0.761 for a decision tree. A model that cannot be beaten is not evidence of
anything.

## 2. `action_tasks.csv` — per-task execution log

**Tasks**: regression (`duration_sec`) and bandit reward (`outcome`).
**Used by**: components 2.2 and 2.5.

| Column | Type | Description |
|---|---|---|
| `session_id` | int | Groups tasks into a user session |
| `task_type` | categorical | 10 types (`run_script`, `open_app`, `send_email`, …) |
| `agent` | categorical | Which of 5 agents handled it |
| `step_count` | int | Sub-steps the task took |
| `hour` | int | Hour of day, 0–23 |
| `historical_avg` | float | Prior mean duration for this task type |
| `duration_sec` | float | **Regression target** |
| `tier` | int | Security tier, 1 or 2 (PRD §9) |
| `routing_arm` | categorical | `direct_dispatch` / `cached_plan` / `planner_llm` |
| `outcome` | categorical | `success` (6,176) / `corrected` (1,479) — the bandit reward |

Durations are drawn from documented per-task profiles in `datagen/config.py`
(base seconds + seconds per step) with noise added. Those numbers are stated
**assumptions of the simulation, not measurements** — the file says so directly.

## Component 2.3 has no file — and that is worth stating

**Memory clustering (2.3)** does not read a CSV. It generates its data in memory
each run: 700 samples drawn as Gaussian clusters around 7 topic centroids —
*Machine Learning Coursework, Project Monday Development, Job Applications &
Internships, Personal Finance & Shopping, Research Papers & References,
Communication & Emails, Desktop Files & Organisation*.

So if asked "where is the dataset for clustering", the honest answer is that it
is synthesised at runtime by `ml/memory_clustering.py` rather than stored. It can
be exported to `data/synthetic/` on request; it simply has not been, because
nothing needed it on disk.

At runtime the same component clusters the **real** memory store
(`data/memory.db`), which is the user's own saved notes and is not committed.

## Provenance — why synthetic, and the honest limitations

**Why generated rather than collected.** The project routes commands to agents
that act on a real desktop — sending email, opening applications, terminating
processes. A collected corpus would consist of one team's commands on their own
machines, carrying their filenames, contacts and habits. Generation gives
balanced classes, a known ground truth, reproducibility from a seed, and no
personal data.

**State this plainly rather than let it be discovered.** The limitations are:

- **The world is simulated end to end.** Durations, outcomes and co-occurrence
  patterns come from the assumptions in `datagen/config.py`. A model fitted here
  learns those assumptions well; it has not been validated against real usage.
- **Metrics are upper bounds.** Real commands are messier than templated ones.
  The 0.929 macro-F1 is the ceiling of this simulation, not a field result.
- **A live gap is already visible.** In live use on 2026-08-10, *"how many files
  are on my desktop"* classified as `chitchat` at **0.25 confidence** — that
  phrasing has no coverage in `datagen/commands.py`. It is a genuine, citable
  example of simulated training data failing on real input, and the honest
  improvement is widening the generator's vocabulary rather than downloading an
  unrelated public corpus.

**One real external dataset is also used**, though not for training:
`data/public_apis.json` (158 KB) is an index of ~780 public APIs derived from the
[public-api-lists](https://github.com/public-api-lists/public-api-lists)
repository, cached locally and searched with TF-IDF by `PublicApiAgent`.
